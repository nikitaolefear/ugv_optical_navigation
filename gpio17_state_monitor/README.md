# GPIO17, STOP_LATCH і RESET

## StateMonitor

Ця ізольована копія реалізує остаточне рішення власника про діагностику
за наявною телеметрією. Попередній проєкт апаратного блокування нижче
збережено як історію. StateMonitor використовує наявний GPIO17, стан
STOP_LATCH, телеметрію Pixhawk і пасивні пакети ESC та SERVO_OUTPUT_RAW.
Вебінтерфейс дістає його через наявний `GET /api/production-stop`
для користувачів із правами перегляду стану й телеметрії.

Напруга відображається за слотами ESC. В архівному спостереженні є 57,93 В
у слоті №3. Для підпису «лівий» або «правий» потрібна підтверджена
прив'язка до слота. Без неї, а також без свіжого значення, показується
`UNKNOWN`. PWM показує повідомлений сигнал, а фізичний стан гальм
позначено `UNKNOWN`. StateMonitor не постачає доказів у production
RESET або MISSION_RESUME.

Адресні офлайн-тести з каталогу копії:

```sh
/opt/ugv-disarm/venv-auth/bin/python -B test_state_monitor.py
```

## Читання маршруту через serial-owner

В ізольованій копії прапорець `--observe-auto-route` підключає читання до
наявного owner. Через його дескриптор і MAVLink encoder ідуть
`MISSION_REQUEST_LIST`, послідовні `MISSION_REQUEST_INT` і завершальний
`MISSION_ACK`. Фактичний `MISSION_CURRENT.seq` береться з потоку
телеметрії. HOME читається окремо як seq 0 і виключається з SHA-256.

Checkpoint використовує завершене свіже зчитування та свіжий seq на фронті
STOP. STOP і прийнятий RESET зберігають спільні STOP ID, seq і SHA-256 у
журналі. Для перевірки перед RESUME потрібно завершене зчитування, розпочате
після STOP. Таймаут, неповне зчитування або втрата зв’язку роблять маршрут
недоступним для перевірки. За наявності firmware plan ID він також
звіряється. На firmware без plan ID перевірка спирається на повне
повторне зчитування і передбачає відсутність стороннього запису маршруту
під час читання.

Прапорець створює лише read-only адаптер, якщо супервізор не передано
окремо. Відсутність фізичного InterlockIO лишає production RESET і
MISSION_RESUME заблокованими.

```sh
/opt/ugv-disarm/venv-auth/bin/python -B test_owner_mission_reader.py
```

Розрив дескриптора скидає часткове читання, поточний seq і дозвіл
відновлення, а в журналі фіксується `MAVLINK_LOST`. Штатний цикл
перепідключення повторно відкриває дескриптор. Нове читання починається з
`MISSION_REQUEST_LIST`. Кожна транзакція використовує наступний MAVLink
component ID для адресованих відповідей місії на тому самому encoder.
Інші повідомлення owner зберігають свій component ID.

Два інтеграційні сценарії запускають повний owner з тимчасовим PTY,
окремим Unix-сокетом і локальним SITL. Для прогону потрібна копія
`eeprom.bin` Rover SITL із трьома waypoint та HOME.

```sh
/opt/ugv-disarm/venv-auth/bin/python -B test_sitl_owner_reconnect.py \
  /path/to/ardurover /path/to/defaults.parm /path/to/eeprom.bin
```

Для двох сценаріїв втрати окремих пакетів із відкритим дескриптором
додати `--packet-loss`. Стенд відкидає відповідь, очікує таймаут, потім
подає затримані відповіді та дублікат під час повторного читання.

Інертний overlay для `WEB_DISARM_VALIDATED` (`1eafb0b`). Файли `frontend_gateway/` відповідають `/opt/ugv-disarm/package`. Файли `owner_externalnav/` відповідають `/opt/ugv-tilted-observe/20261117/package`. `base-sha256.json` фіксує встановлену версію кожного заміненого файла. Для підготовки майбутнього релізу накладати overlay на повні копії відповідних баз. Обидва екземпляри `disarm_control/ipc.py` потрібні, бо owner і gateway імпортують модуль із різних пакетів.

## Межа програмної інтеграції

Встановлений owner отримує FRONT з того самого GPIO17 monitor. Невідома чи прострочена вибірка фіксує STOP. Serial tick продовжує викликати DISARM engine, maintenance tick, diagnostics та ExternalNav у попередньому порядку. Код навігації, оптичні активи, авторизація і schema DISARM ledger беруться з бази. UUID і рішення RESET зберігаються в окремій приватній SQLite DB owner.

Frontend читає FRONT і latch через gateway та використовує поточний RESET у блоці місій. Поточні CSS, кнопка RESET і верхні кнопки ARM/DISARM зберігаються. Для RESET потрібні `stop.reset`, session, CSRF і перевірка походження. Докази безпеки надходять від owner. Дозвіл видається лише після підтвердження trusted interlock, свіжих RELEASED і DISARMED, нерухомості, підтвердженого блокування тяги та відсутності активних STOP/DISARM транзакцій. RESET знімає програмний latch і за увімкненого гальмівного профілю запускає контрольоване відпускання гальм. Тяга лишається заблокованою до окремого фізичного дозволу. Надсилання команди відпускання не підтверджує механічний стан гальм. Gateway за замовчуванням тримає RESET OFF, а production entry point ще не має апаратного provider.

## Апаратне блокування тяги

### Факти

Контрольна точка 2026-11-02 фіксує Pixhawk Rover 4.7.2, керування задніми колесами через DroneCAN і `CAN_D1_UC_ESC_BM=15`. У поточній телеметрії є свіжий `ESC_TELEMETRY_1_TO_4` від Pixhawk 1/1 та 57,93 V у слоті ESC 3. Цей зріз не встановлює відповідності CAN-вузлів колесам або маршруту силового живлення. RC-пакет свіжий, канали порожні, Pixhawk повідомляє `PreArm: Radio failsafe on`. Проходження активної команди від ELRS через Pixhawk до обох VESC у цьому сеансі не підтверджено. Оператор підтвердив загальне відключення АКБ через E-STOP. Тип відсікача, точки розгалуження та електрична схема гальма лишаються невідомими.

### Цільова схема

Чинний фізичний E-STOP повністю відключає АКБ, включно з Pi, Pixhawk та обома VESC. Зберегти цей контур. Після E-STOP потрібні окремі гілки керування (Pi/Pixhawk/діагностика) та тяги (обидва VESC), щоб бампер міг блокувати тягу зі збереженням HMI. Використати наявний незалежний канал блокування тяги, якщо його буде знайдено й перевірено для обох VESC. Якщо такого каналу немає, встановити контрольоване силове відсікання лише в гілці VESC. Номінали, кількість силових елементів, передзаряд і розряд визначаються після перевірки реальної схеми та документації VESC. Чинний загальний E-STOP залишається upstream, без нової паралельної лінії живлення.

| Звідки | Куди | Призначення |
| --- | --- | --- |
| Двоканальний контакт бампера | Контрольовані входи тягового interlock | Знімає дозвіл для обох VESC незалежно від Pi, ELRS та Web ARM. |
| Тяговий interlock | Наявний незалежний відсікач або контрольовані контактори тягової гілки | Фактичне відсікання з фізичним зворотним зв'язком. |
| Ізольований статус бампера | GPIO17 | FRONT для owner. |
| Ізольований heartbeat від Pi | Апаратний watchdog | STOP_LATCH або зникнення імпульсів знімають дозвіл. Після power-on виходи вимкнені. |
| Interlock і вимірювання VESC та коліс | Ізольовані входи Pi | Позитивні докази для RESET. Поточний адаптер очікує K1/K2 і підтвердження безпечної напруги. Якщо знайдено інший придатний відсікач, схему доказів треба прив’язати до його реальних сигналів. |

Окрема фізична кнопка повторного пуску підключається до контролера. Контролер має ігнорувати утриману кнопку і вимагати нового фронту після повернення справних входів та heartbeat. Після Web RESET owner може відновити лише heartbeat. Перезапуск контакторів залишається окремою фізичною дією. Відсікання джерела саме по собі допускає вибіг. Верифікація гальма та безпечної поведінки шини при рекуперації потрібна до приймання. Якщо наявне гальмо діє через VESC, його не можна зараховувати як утримання після відсікання.

### Три перевірки на місці

1. Простежити, що розмикає E-STOP, куди йдуть NC контакти E-STOP і бампера, чи є незалежна тягова гілка до обох VESC та дзеркальні контакти на наявному відсіканні. Зафіксувати маркування VESC та можливі паралельні джерела живлення.
2. Простежити сигнал гальма від джерела до виконавчого вузла. Встановити, чи гальмо механічне або VESC-рекуперативне, що відбувається при втраті живлення, і чи існує фактичний сигнал накладеного гальма.
3. Підтвердити розводку ELRS → Pixhawk і CAN → два тягові VESC за проводкою та мітками вузлів. Ідентифікувати незалежні точки підтвердження напруги downstream обох VESC та нерухомості обох коліс.

### Candidate і приймання

`HardwiredInterlock` підключається до чинного GPIO monitor через ін'єкцію `InterlockIO`. Штатний entry point запускається без фізичного драйвера I/O, поки його тип і проводка невідомі. Обмін I/O має бути обмежений за часом та працює у потоці monitor. Під час ARM/RESET owner перевіряє лише кеш із часом найстарішої вибірки. `physical_drive_interlocked` вимагає позитивного підтвердження відсікання, а RESET додатково вимагає нерухомості та штатного DISARMED. Помилка, повтор кадру або прострочене підтвердження закриває дозвіл. Реле/контактор спрацьовує за апаратним watchdog навіть при зависанні Pi. Інтервал watchdog і час розмикання необхідно виміряти на стенді, окремо від програмного ліміту свіжості 0,5 с.

Спочатку перевірити входи, EDM, гальмо, сигнал напруги та watchdog зі знеструмленою тяговою гілкою. На ізольованому стенді з імітаторами навантаження перевірити обрив NC, вимкнення Pi, застиглий вихід heartbeat, залипання одного контактора, втрату readback і відсутність повторного пуску після RESET. Після окремого погодження перевірити напругу downstream, час відсікання і поведінку гальма на закріпленому ровері. Ці апаратні випробування ще не виконувалися.

## Повна втрата живлення

STOP і RESET використовують приватну SQLite DB owner `disarm.sqlite3.stop-reset.sqlite3`. Поточний стан та подія записуються однією атомарною транзакцією. Для RESET та сама транзакція містить UUID і рішення. Використано rollback journal DELETE і `synchronous=EXTRA` для fsync журналу, DB і каталогу під час commit, а після відкриття каталог синхронізується явно. Історія містить FRONT-переходи, переходи latch, RESET і кожен старт owner із boot ID. Старі UUID RESET зберігаються під час міграції.

На кожному старті owner, включно з рестартом у межах того самого boot, RAM і запис STOP починаються з latch ON. Минуле `RESET_ACCEPTED` зберігається як історія. Пошкоджена, недоступна, неповна або логічно неузгоджена DB залишає STOP зафіксованим, RESET заблокованим і файли для перевірки. Помилка commit блокує програмний дозвіл тяги. У цій ситуації DISARM та навігація продовжують користуватися власними незалежними шляхами. SQLite відновлює незавершену транзакцію за rollback journal, якщо це можливо. Коли живлення зникає до першого запису події, журнал може не містити причини відключення. Наступний запуск усе одно фіксує STOP. Стендове приймання має перевірити поведінку реального носія й апаратний interlock при зникненні живлення.

Після повернення АКБ оператор перевіряє ситуацію та окремо підтверджує програмний RESET за свіжих RELEASED, DISARMED, нерухомості, відсікання тяги та відсутності активної DISARM транзакції. У стендовому гальмівному профілі watchdog тяги лишається вимкненим після RESET і відпускання гальм. ARM вимагає окремого запиту й активації на поточний boot.

## Web ARM

Наявна зелена кнопка ARM використовує чинний frontend → gateway → serial-owner. Усі три рівні вимагають окремого opt-in для поточного boot. Frontend і gateway також вимагають активованого Web DISARM. Право `pixhawk.arm` видається явно. Сесія, CSRF і Origin перевіряються тим самим middleware, що й для DISARM. ARM ledger окремий. Owner фіксує спробу до запису, повтор UUID повертає старий статус, перезапуск перериває незавершені транзакції без повтору. Лише новий свіжий HEARTBEAT того самого Pixhawk після повного запису дозволяє зберегти `ARMED_OBSERVED`. Команда використовує штатний `MAV_CMD_COMPONENT_ARM_DISARM` з `param1=1` і `param2=0`.

Owner перевіряє всі умови при прийманні запиту та перед записом. Потрібні DISARMED у HOLD/STANDBY, свіжий SYS_STATUS з увімкненими й здоровими PreArm та RC receiver, відсутність несправних увімкнених підсистем, скинутий STOP_LATCH та свіже підтвердження interlock. Вимога HOLD запобігає arming в активному режимі й використовує штатний сигнал STANDBY Rover. Provider має повернути монотонний час останнього підтвердження справного interlock із фізично заблокованою тягою через `arm_gate_verified_at()`. У поточному candidate provider відсутній. RESET не викликає ARM. DISARM скасовує ARM у черзі до запису та має пріоритет у serial tick. Після вже здійсненої спроби ARM DISARM іде штатним шляхом, а незавершений результат ARM позначається UNKNOWN.

### План встановлення

1. Виконати адресні тести на копіях баз. Підготувати окремі root-owned релізи з overlay та зафіксувати їхні контрольні суми. Зберегти узгоджені копії чинних unit/drop-in, баз authorization/DISARM та їхніх digest.
2. За окремим погодженням виконати cutover із заблокованою тягою, зберігши одного serial-owner. Спочатку перевірити штатний DISARM, історію ledger, ExternalNav і стан GPIO17 з ARM OFF. Перевірити STOP gate та RESET за планом апаратного приймання. Відсутні підтвердження залишають ARM і RESET заблокованими.
3. Після апаратного приймання, усунення Radio failsafe та окремого дозволу оператора додати поточний boot UUID лише в runtime drop-in owner/gateway як `--web-arm-boot-id` і frontend як `UGV_WEB_ARM_BOOT_ID`. Видавати `pixhawk.arm` лише уповноваженим операторам. Спершу перевірити GET readiness. Реальна команда ARM потребує окремого погодження.
4. Для відкату прибрати ARM opt-in та повернути перевірені попередні релізи й unit/drop-in контрольованою зупинкою та запуском одного owner. Зберегти робочі DB та нові журнали ARM і RESET. Після reboot UUID зміниться і ARM лишиться OFF.

## Web DISARM після reboot

Використати штатний root-owned `channel_ops.py` з відповідним `cutover.py` і `activate_stock_tx.py`. Перевірені копії є в `milestones/WEB_DISARM_VALIDATED/operations`. Спочатку запустити helper без прапорів для preflight. Після відновлення свіжих RC5 DISARM і RC3 neutral, успішного preflight та окремого дозволу оператора використати режим `--activate --operator-approved`. Він відновлює runtime drop-ins і знімає inhibit під час контрольованого перезапуску служб. Результат `CHANNEL_ENABLED_NO_COMMAND_SENT` підтверджує готовність каналу без команди, а helper звіряє digest ledger після перезапуску. Штатний helper перевіряє stock owner за встановленими hashes, тому для майбутнього розгортання overlay його перевірки потребують перегляду під новий реліз.

## ExternalNav alignment окремо

З наявними картою та калібруванням підтвердити фізичне положення камери й HOME. Для штатного `activate_stock_tx.py` потрібен погоджений перехід у stock observe-only та відкладення старого grant і TX drop-in. Зібрати свіже HOME evidence для поточного boot, виконати `--check --home-evidence <файл>`, потім застосувати штатний `--enable` з операторськими підтвердженнями. Поточний TX-процес зі старим grant і порожні RC-канали не відповідають preflight. Після погодженої активації перевірити `alignment_verified=true` та зростання `sent`. Калібрування повторювати не потрібно.

## Checkpoint AUTO в ізольованій копії

На переході GPIO17 до `PRESSED` owner звіряє свіжі AUTO/ARMED і
`MISSION_CURRENT` та зберігає в RAM waypoint, SHA-256 і ID події STOP.
Журнал FRONT містить ці значення. Канонічний маршрут використовує впорядковані
`MISSION_ITEM_INT` із координатами у wire-форматі, нормалізованими float32
і виключеним динамічним HOME (seq 0). Перезапуск втрачає дозвіл на відновлення.
Штатний RESET прив’язує свій UUID до checkpoint, а окремий запит оператора
`MISSION_RESUME` ставить відновлення waypoint у чергу.

Перед записом owner повторно перевіряє інтерлок, фізичні докази, прив’язку
RESET і SHA-256 повторно зчитаного маршруту. Після одного
`DO_SET_MISSION_CURRENT` потрібні ACK ACCEPTED і свіжий
`MISSION_CURRENT` із збереженим seq. Лише тоді owner передає запит
супервізору. Нова подія FRONT або невизначений результат анулює спробу.
Статус RUNNING окремо вимагає свіжого AUTO/ARMED та активної місії.

`RoverAutoAdapter` приймає ін’єкцію кешу повного зчитування маршруту,
MAVLink sender і фізичного дозволу. Хост має виключити одночасний запис
маршруту та очищати кеш при втраті зв’язку або початку зміни місії.
Штатний entry point лишається без фізичного `InterlockIO` і з вимкненими
production ARM, AUTO та RELEASE.

Адресний прогін використовує Rover SITL 4.7.3, його штатний
`Tools/autotest/default_params/rover.parm` і лише UDP loopback. GPIO, RESET,
фізичний дозвіл та IPC handoff у цьому прогоні імітуються. Пакети маршруту,
ACK і `MISSION_CURRENT` надходять від Rover SITL.

```sh
python -B sitl_checkpoint_scenario.py /path/to/ardurover /path/to/rover.parm
```
