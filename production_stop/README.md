# production_stop

Ізольоване Python-ядро для FRONT / REAR / LEFT / RIGHT. Не імпортує
експериментальний StopLatch / HoldBench, не відкриває GPIO або MAVLink,
не змінює HMI, конфігурацію чи systemd.

## Встановлені та заплановані компоненти

Фізично встановлений тільки передній NO-бампер: FRONT, BCM GPIO17,
input pull-up; HIGH = RELEASED, LOW = PRESSED. Ізольоване ядро лише
декларує це призначення, не налаштовує й не читає GPIO.

| Зона | Поточний стан встановлення | BCM GPIO |
| --- | --- | --- |
| FRONT | Встановлений | 17 |
| REAR | NOT_INSTALLED, запланований | Не призначений |
| LEFT | NOT_INSTALLED, запланований | Не призначений |
| RIGHT | NOT_INSTALLED, запланований | Не призначений |

REAR, LEFT і RIGHT не вважаються захищеними. Поточна система не забезпечує
повного кругового захисту. NOT_INSTALLED не означає RELEASED або безпеку.

За замовчуванням `StopController()` використовує незмінний `DEFAULT_INPUTS`:
`(BumperInput(Zone.FRONT, 17),)`. Для розширення потрібно передати `inputs=`
із явним BumperInput для кожної встановленої зони. BCM GPIO для майбутніх
зон тут не призначені. Порожня конфігурація, повтори зон або GPIO заборонені.
Конфігурація фіксується при створенні контролера; новий екземпляр стартує
з STOP_LATCH. Зміна фізичного складу не виконується через update().

## Контракт станів

- Старт: STOP_LATCH=true, встановлені контакти UNKNOWN, решта NOT_INSTALLED,
  motion_permitted=false.
- PRESSED, UNKNOWN, відсутній або прострочений сигнал будь-якої сконфігурованої зони
  встановлює STOP_LATCH. Відновлення RELEASED не скидає latch.
- Свіжість і достовірність перевіряються тільки для встановлених входів.
  Відсутність FRONT завжди блокує дозвіл. NOT_INSTALLED — лише вихідний
  статус: передача його для встановленого входу дає UNKNOWN.
- update() для несконфігурованої зони встановлює latch та піднімає ValueError;
  така зона залишається NOT_INSTALLED. Це помилка конфігурації адаптера.
- Сигнал свіжий лише коли 0 <= age < freshness_s (типово 0.5 с).
- Невідоме значення контакту, некоректна, майбутня, повторна чи зворотна
  часова мітка перетворюють відповідний вхід на UNKNOWN.
- Мітки приймаються лише як вбудовані int/float. None, bool, рядки,
  контейнери, числові підкласи, NaN/Infinity та надмірні значення
  (зокрема 10**1000) відхиляються без OverflowError. Для показань це
  означає UNKNOWN і STOP_LATCH, навіть якщо раніше рух був дозволений.
- Зворотний або нескінченний/NaN годинник блокує контролер до створення
  нового екземпляра. Новий екземпляр завжди стартує з latch.
- Некоректний тип або виняток джерела часу також встановлює постійний
  CLOCK_FAULT і блокує дозвіл.
- Snapshot незмінний; публічні операції захищені спільним RLock.

## RESET і START

Консервативна політика ядра вимагає свіжі RELEASED від усіх сконфігурованих входів
(зараз тільки FRONT) та свіжі ResetConditions із явними
True для disarmed, stationary, hold_confirmed, stop_transaction_idle.
Відсутність, False або застарілі підтвердження відхиляють RESET.
Кожен відхилений RESET встановлює STOP_LATCH і відкликає попередній
програмний дозвіл руху. Некоректна мітка підтверджень не змінює показань
бампера й не спричиняє часткового очищення latch.
Конкретні джерела підтверджень, пороги нерухомості та їхню придатність
потрібно перевірити перед підключенням до живої системи.
observed_at — найстаріше зі спостережень, на яких базуються підтвердження;
повторне читання кешу не оновлює його час.

reset() повертає (accepted, snapshot). RESET лише очищує програмний
latch; не надсилає команд і не відновлює місію. motion_permitted — лише
одна необхідна умова загального дозволу руху, не команда ARM/руху.
START має бути окремою явною командою майбутнього supervisor із повторною
перевіркою всіх дозволів безпосередньо перед виконанням. У ядрі немає
START, автоматичного запуску чи збереженої команди для відкладеного виконання.

## Межі майбутніх адаптерів

1. GPIO reader має регулярно подавати кожну встановлену зону через update() з часом
   фактичного зчитування у спільному monotonic clock domain. Помилка
   читання -> UNKNOWN. Без observed_at часом зчитування вважається час
   виклику, тому цей режим придатний лише для синхронного reader.
   Явне observed_at=None вважається помилкою; для синхронного режиму
   аргумент потрібно пропустити.
2. Supervisor має викликати tick() незалежно від надходження сигналів
   і перевіряти актуальний snapshot перед кожною командою руху.
   Збережений snapshot не є довготривалим дозволом.
3. Окремий виконавець STOP/HOLD має обробляти latch та підтвердження
   автопілота. У цьому модулі такого виконавця немає.
4. Умови RESET надходять від довіреного supervisor, не напряму з UI.
   Ядро перевіряє передані підтвердження, але саме не вимірює швидкість,
   стан ARM чи режим Pixhawk.

`interfaces.py` містить лише контракти, без реалізації транспорту:

- `StopStatePort`: update / snapshot / tick / reset для supervisor.
- `SafetyEvidenceProvider`: майбутнє джерело ResetConditions; за відсутності
  достовірних даних повертає None, що ядро відхиляє при RESET.
- `snapshot_payload`: окрема JSON-сумісна копія стану для HMI з
  NOT_INSTALLED для відсутніх зон та installed_inputs з призначеннями BCM GPIO. UI запитує
  RESET у supervisor; не встановлює прапорці безпеки самостійно.

Публікація payload не перевіряє час повторно: supervisor має одразу перед
нею отримати snapshot(). Жоден із цих інтерфейсів не відкриває портів,
не надсилає HOLD і не викликає чинні HMI або HoldBench.

## Незалежний апаратний E-STOP та обмеження

Потрібен окремий незалежний апаратний E-STOP, який припиняє тягу навіть
при зависанні Raspberry Pi, втраті зв'язку або неспрацюванні HOLD.
Програмний HOLD не є достатнім фізичним захистом. Апаратна схема,
вплив на приводи, процедура відновлення та перевірка E-STOP залишаються
окремою роботою; цей модуль їх не реалізує і не підтверджує.

Строк 0.5 с — параметр для тестів, не підтверджений час реакції ровера.
Потрібні окремі рішення про GPIO для майбутніх зон, діагностику проводки,
фільтрацію контактів, частоту опитування та поведінку виконавця STOP.
NO-контакт із pull-up не виявляє обрив проводу: HIGH сам по собі не дозволяє відрізнити звільнений контакт
від обриву проводу. Ядро не гарантує виявлення такої апаратної несправності.
При зависанні процесу Python ядро не виконає STOP; потрібен незалежний
механізм контролю та апаратного припинення руху.

## Перевірка без обладнання

```sh
python3 -m unittest discover -s tests -p 'test_production_stop.py' -v
```

Результат перевірки 2026-11-16: 31 unit-тест пройшов. Перевірені
стартове блокування, кожна зона PRESSED/UNKNOWN, відновлення без автоскидання,
точна межа свіжості, пропуск tick, час фактичного зчитування, некоректні
мітки, регресія та NaN/Inf годинника, умови RESET і копія даних HMI. Окремо перевірені FRONT-only / GPIO17,
NOT_INSTALLED, відсутність і прострочення FRONT, ручний RESET після відпускання,
відхилення некоректної конфігурації та розширення до чотирьох входів.
GPIO інших зон у тестах синтетичні й не є планом реального підключення.
Тести використовують керований годинник; не потребують GPIO, serial або мережі.

P0-регресії: зі стану motion_permitted=True надходить PRESSED або UNKNOWN
із observed_at=10**1000 — результат STOP_LATCH=True, motion_permitted=False,
без винятку. Додатково перевірені матриці неправильних міток для показань
і RESET, неправильні підтвердження RESET із попереднього дозволеного стану,
межі свіжості, відновлення тільки через ручний RESET та відмова годинника.

Готові ядро станів, контракти майбутніх адаптерів і unit-тести.
Не перевірені реальні входи, затримка фізичної зупинки, незалежний E-STOP,
Pixhawk/HMI-адаптери та поведінка при відмовах живої системи.
Чинні служби, GPIO, systemd, stop_latch_test і робочий HMI не змінювались.
Розгортання та інтеграція з роботом потребують окремого дозволу.
