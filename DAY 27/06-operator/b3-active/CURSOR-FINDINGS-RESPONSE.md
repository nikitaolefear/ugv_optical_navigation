## Lock order

BenchOperator uses threading.RLock. Dispatch takes operator.lock then B3 lock. B3 tick uses the same order. In the audited source operator_status did not acquire operator.lock recursively; the PTY regression also exercises recursive acquisition of this RLock. No self-deadlock reproduced. Do not introduce an inverse B3-to-operator acquisition from another thread. Transitive marker reads, alignment asset hashes and syscall are still under the guard/lease critical section. The test for revoke during send and synthetic long qualification cannot put a hard bound on real filesystem I/O. Review this before deployment. Client request timestamp covers handler and lock delay; supervisor uses time before sending a signal as conservative lower bound for the exit event and the pidfd as upper observation.

## B3 firmware behavior and future readback

In Rover 4.7.2 the ODOMETRY handler checks LOCAL_FRD/BODY_FRD before passing pose and velocity to VisualOdom. The MAV backend applies a quality threshold and logs/updates backend data even when the estimate is ignored. A value of -1 alone cannot guarantee no changes and is not the main defense. B3 sends a well-formed ODOMETRY frame with valid enumerated LOCAL_NED/BODY_FRD and synthetic payload to take the release-specific early frame-rejection branch. Confirm build/handler and links before live use. B4 must use its separately approved valid estimator input stream. Record absent fields explicitly. Compare current trusted SRC, firmware release, clock anchor and configuration. No parameter request was made in this audit.
