# LOG_DISARMED — ізольований транзакційний helper

**Готовність до live тесту — NO.** Реалізовано транзакційне ядро, побудову двох фіксованих MAVLink повідомлень і перевірки доказів. Чинний Owner не реєструє цей endpoint. Потрібні інтеграція з чергою Owner, звірення identity/authorize від реальних джерел, профільний helper і стендові інтеграційні тести. B2 не змінювався.

## Контракт і recovery

Запити begin, restore і recover не приймають імені чи значення параметра від клієнта. Початок робить окремий PARAM_REQUEST_READ для LOG_DISARMED, пише durable enable_intent з baseline, потім допускає тільки значення 1. Для readback потрібен новий PARAM_REQUEST_READ, відповідь з 1/1, точне ім'я і тип. Ехо PARAM_SET не є readback. Протокол PARAM_VALUE не має nonce, тому інтеграція має серіалізувати параметричний трафік, завершити чи ізолювати попереднє вікно відповіді, відкидати старі/проміжні відповіді й відмовлятися за неоднозначного походження readback.

Журнал призначений для окремого приватного каталогу на постійному диску. Використано ексклюзивний lock, закриті права, fsync файла, атомарну заміну, fsync каталогу, контроль структури та digest. Перед будь-яким записом має бути перевірений відповідний intent. Зберігати stable hardware identity, boot epoch Pixhawk, boot Pi та покоління Owner. Новий begin відхиляється за незакритого intent або пошкодженого журналу. Після падіння запуск лише читає незавершений стан. Відновлення дозволяє лише збережений baseline і лише після окремої авторизації під ID транзакції, із перевіркою того самого обладнання, поточної сесії й актуального значення. Якщо вже baseline, повторний запис не потрібен. Якщо актуальне значення відмінне і від baseline, і від 1, зупинитися для reconciliation. Незалежно перечитати baseline перед станом restored. До його підтвердження лишити журнал незакритим. SRC і ExternalNav ці операції не змінюють.

## Майбутній deployment

Під’єднати вузький dispatcher лише до окремо погодженого B2-LOG overlay через чинний SO_PEERCRED, без експорту raw packets, і прив’язати рішення до boot-bound marker та покоління процесу. IPC виконує fsync поза telemetry tick. У черзі sole Owner перевірити guards повторно на відправці, використати один bounded pending exchange, скасувати прострочені запити та виключити конфліктні завдання. Контракт перевіряє свіжий heartbeat, HOLD, DISARMED, inhibit, STOP latch, фізичну ізоляцію, TX disabled, TX=0 та одного Owner. Окремо провести mock startup/rollback саме нового профілю. Чинний B2 та його parser залишаються baseline. Команди live deployment поки відсутні.

## Доказ росту DataFlash і час

1. Через наявний read-only transport зберегти каталог до зміни, UTC/monotonic bracket і завершення LOG_REQUEST_END. Звірити guard, baseline та свіжі дані Observer.
2. Після дозволеного enable з незалежним LOG_DISARMED=1 узяти два рознесені каталоги. Для всіх каталогів потрібен COMPLETE і LOG_REQUEST_END. Ідентифікувати один BIN за однозначним приростом розміру між двома післязмінними каталогами, відстежити новий або вже наявний ID щодо початкового каталогу. Не покладатися на некоректний LOG_ENTRY time_utc; за ротації або повторного використання ID без доказу тотожності результат INCONCLUSIVE.
3. Читати обмежений префікс через Owner і завершити LOG_REQUEST_END. DFReader має знайти FMT та XKFS.SS для C=0 і C=1 всередині того самого перевіреного часового вікна. Якщо префікс старіший або не має обох ядер, результат INCONCLUSIVE. За окремо погодженого bounded read потрібна відповідна ділянка BIN. Зіставити SS з нуль-базованим значенням довіреного S3SRC1, не інтерпретувати це як доказ aiding.
4. Отримати два нові nonce-корельовані TIMESYNC від 1/1, що обрамляють вимір. Зберегти обидві межі Pi monotonic/UTC, RTT/похибку та tc1. Перевірити, що немає reset, UTC step або зміни USB/Owner. Для тотожності boot перевірити в Rover, що конкретний timestamp TIMESYNC походить від boot clock та що writer XKFS ставить той самий boot clock у TimeUS. Додатково прив’язати час свіжих записів до свіжого S3SRC1 з millis() і до свіжого boot time в штатній телеметрії. Перевірити принаймні дві узгоджені ділянки DataFlash, що відповідають часу початку росту і наступного каталогу в межах похибки. Без читабельного запису того самого boot у відповідному інтервалі зв'язок залишити INCONCLUSIVE. Сам збіг тривалості або SS недостатній. [TIMESYNC у Rover 4.7.2](https://raw.githubusercontent.com/ArduPilot/ardupilot/Rover-4.7.2/libraries/GCS_MAVLink/GCS_Common.cpp#L3492-L3564)
5. Після збору доказів виконати окремо погоджений restore, з незалежним readback. За timeout або втрати guard призупинити обмін і лишити journal для explicit recovery через той самий Owner, без автоматичного запису.

## EADDRINUSE

Після штатної зупинки попередній файловий Unix socket лишився на диску, bind завершився EADDRINUSE. Перевірити фактичний socket з аргументів Owner, PID=0, нуль serial owners, тип socket без symlink та відсутність слухача і з’єднань у привілейованому ss -xap. Лише тоді вручну прибрати цей inode і повторити штатний start. Така перевірка не потребує зміни штатної процедури або автоматичного unlink.

## Тести

13 Python PASS з чинним parser, synthetic peer, реальним pymavlink codec і аварійним завершенням окремих процесів до та після імітованого запису. Покриття включає timeout, пошкоджений journal, помилковий readback, втрату heartbeat після durable intent, підміну обладнання, зміну boot, блокування незавершеного recovery, rollback і захист звичайного B2. Три наявні mock shell-сценарії повернення до B2 також пройшли. Вони стосуються попереднього overlay і не є перевіркою deployment B2-LOG. Live трафік і записи відсутні.
