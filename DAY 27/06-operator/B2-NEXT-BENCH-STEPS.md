# Наступний стендовий етап після B2

Статус B2: PASS для read-only. Вихідні спостереження: Rover 4.7.2, SCR_ENABLE=1, SCR_HEAP_SIZE=204800, MEMINFO freemem32=355008, LOG_DISARMED=0, 74 записи у каталозі. Поточний SRC невідомий. Історичний XKFS із ID 74 не підтверджує поточний SRC. Обладнання працює в read-only B2. Наведені зміни потребують окремих дозволів.

## SD та SRC observer

1. Перед доступом до SD оператор підтверджує фізичну ізоляцію тяги, нерухомість, HOLD, DISARMED, штатний stop/inhibit та TX=0. Окремо погодити безпечне вимкнення саме Pixhawk: контролер може залишатися під живленням через USB або інший вхід. SD не вилучати під живленням. Не використовувати паралельного активного serial-клієнта.
2. Змонтувати SD на окремому ПК **тільки для читання**. Зберегти весь APM/scripts до нового приватного backup-каталогу, включно із вкладеними файлами, та скласти відносний список файлів і SHA256. Звірити backup з оригіналом. Перевірити дублікати з однаковими назвами без урахування регістру, посилання на S3SRC1, інші джерела SRC, а також наявні brake/mixer scripts. Локальні копії brake і mixer у репозиторії не є доказом вмісту SD. Зіставити їхні хеші, якщо доступні затверджені еталони. Не публікувати фактичний інвентар SD, ідентифікатори чи сирі логи.
3. Observer використовує лише ahrs:get_posvelyaw_source_set(), millis() і gcs:send_text(). Індекси getter 0/1/2 відповідають SRC1/2/3. Інтервал повідомлення — 500 мс. Перевірити офлайн luac -p та SHA256 затвердженої копії. Якщо існує stage3_src_observer.lua, дубль S3SRC1, помилки скриптингу або невідоме походження brake/mixer — зупинитися. SCR_ENABLE уже дорівнював 1. MEMINFO не є виміром вільного Lua heap; параметри scripting не змінювати для обходу помилок. Зберегти чинні scripting/pre-arm checks.
4. Лише після окремого дозволу на запис підключити SD для запису, додати єдиний новий файл APM/scripts/stage3_src_observer.lua через створення без перезапису (підтвердити відсутність імені та регістронезалежних дублів). Перевірити digest нового файла та відсутність будь-яких інших змін у маніфесті. Синхронізувати й відмонтувати носій. Повернути SD на вимкненому Pixhawk. Після ввімкнення отримати нову часову прив’язку, знову підтвердити HOLD/DISARMED і brake/STOP baseline. Не перезапускати всі скрипти окремою MAVLink-командою.
5. На чинному B2 через дозволений операторський інтерфейс перевірити цільове джерело, профіль, Lua startup/heap warnings та TIMESYNC. Після ручної перевірки ідентичності плати й файла створити лише передбачену операторською інструкцією boot-bound локальну атестацію його SHA256. Peer/SYSID/COMPID самі по собі не є доказом походження. Зібрати кілька послідовних зразків приблизно раз на 500 мс. Вік за локальним readback менше 1 с, час FC зростає, replay відхиляється, clock anchor свіжий. B2 статус отримувати у межах вікна свіжості після TIMESYNC. Після reset FC не приймати старого boot-якоря або колишню атестацію як доказ актуальності. За відсутності статусу лишити SRC UNKNOWN; не перемикати його для діагностики. Getter — стан AHRS; стан окремих ядер та aiding перевіряються окремо.
6. Видалення потребує окремого погодження. Припинити довіру до атестації, узгоджено вимкнути FC, на SD звірити hash доданого observer і видалити лише його. Звірити весь решта APM/scripts з baseline, відмонтувати. Після повернення носія перевірити відсутність S3SRC1, штатну роботу brake/mixer і HOLD/DISARMED/TX=0. Не відновлювати живлення тяги.

Джерело API: [Rover 4.7.2 scripting bindings](https://raw.githubusercontent.com/ArduPilot/ardupilot/Rover-4.7.2/libraries/AP_Scripting/generator/description/bindings.desc).

## Окремий LOG_DISARMED-only допуск

Поточний B2 не має запису. Не використовувати загальне налаштування параметрів або повний Stage 3 lease. З наявного кандидата повторно використати durable baseline, allowlist і окремий PARAM_REQUEST_READ; спеціалізувати майбутній recovery port **тільки** для LOG_DISARMED. Поточний загальний recovery helper перевіряє також SRC, тому для цього сценарію його не застосовувати без спеціалізації. Невідомий SRC зберігається як UNKNOWN і не змінюється.

- Один Owner, той самий UID-перевірений Unix IPC. Окреме право оператора на єдину транзакцію. Дозволені дії: read LOG_DISARMED, встановити лише 1, відновити лише збережене вихідне значення. Без довільного PARAM_SET, нових портів чи ExternalNav lease.
- Перед записом підтвердити свіжий HOLD/DISARMED/heartbeat, фізичну ізоляцію, inhibit, STOP latch, TX=0 та відсутність catalog transfer. Перечитати LOG_DISARMED через чинний Owner. Незалежно перевірити ідентичність FC, live параметр і профіль. Не припускати, що майбутнє початкове значення все ще 0.
- До першого write атомарно записати і fsync-нути приватний baseline: версію, ідентифікатор операції та FC, початкове значення, заплановане 1, стан PENDING і час. fsync каталогу, 0600 для файла, 0700 для каталогу, checksum і блокування конкурентних операцій. Дочекатися підтвердження commit журналу.
- Окремо погоджена одноразова зміна до 1 через штатний writer Owner. Окремий PARAM_REQUEST_READ після завершення запису. Приймати свіжий цільовий PARAM_VALUE саме LOG_DISARMED, значення 1; підтвердити відсутність інших змін. ACK або повернення з send не закривають транзакцію. Невизначеність, timeout і crash залишають PENDING та блокують нові мутації.
- Для restore або recovery після аварії знову підтвердити ізоляцію/TX=0 та особу FC, відкрити приватний journal з перевіркою цілісності й перечитати LOG_DISARMED. Після явного дозволу відновити тільки baseline. Якщо значення вже вихідне, запис не потрібен. Повторити незалежний readback і перевірити штатний профіль, залишити останній журнал і артефакти. Лише після підтвердження позначити COMPLETE. Немає автоматичного запису після restart та немає дії SRC.
- До live потрібні огляд і офлайн-тести справжнього вузького IPC-порту: відмова UID/дозволу, втрата відповіді, owner crash після можливого write, помилка readback і re-entry. Наявні mock-тести журналу та загального restore не замінюють ці тести.

## Доказ росту DataFlash

Перед погодженим записом отримати каталог ID/size через B2 і завершити END. Після readback LOG_DISARMED=1 та за справних guard отримати ще два знімки з виміряною паузою (початково близько 10 с; визначити за фактичним flush). Після кожного LOG_REQUEST_END має бути відправлено, а heartbeat лишатися свіжим. Не опитувати каталог під час основного вікна або одночасно з іншими diagnostics jobs. Вимагати збільшення байтів одного однозначного ID, що з'явився або продовжився після зміни. Якщо ID ротується без однозначної прив'язки, статус INCONCLUSIVE. Не використовувати каталожну дату.

Для нового ID прочитати лише обмежений префікс, перевірити SHA256, FMT і XKFS за обома ядрами, після END підтвердити новий приріст. Відрізнити очікуваний кінцевий обрив bounded prefix від пропусків усередині. Зв'язок з FC boot epoch, TimeUS і співставлення VPE.usec/VISP.RTimeUS потрібні для основного Stage 3, а не для самого доказу росту. За відсутності росту зупинити підготовку і погоджено повернути параметр. Повний файл за цим кроком не потрібен.

## B3 hardware і розподіл робіт

Системні метадані вже відкритого дескриптора Owner підтверджують USB CDC ACM Full Speed 12 Мбіт/с на composite USB-пристрої. Для цього шляху потрібні пасивний inline USB protocol analyzer з Full Speed capture (наприклад [Beagle USB 12](https://www.totalphase.com/products/beagle-usb12/) або [Beagle USB 480](https://www.totalphase.com/products/beagle-usb480/)), відповідні USB data-кабелі, окремий capture ПК, timestamping і декодер MAVLink у CDC bulk payload. За наявності апаратного trigger використовувати його; інакше зафіксувати спільну унікальну контрольну подію у trace/capture, оцінити похибку до запуску. GPIO UART logic analyzer не вимірює цей USB шлях. Host usbmon може бути додатковим доказом, але не підтверджує фізичний останній кадр.

Codex: звірка інвентарю/хешів після отримання приватної копії, офлайн Lua та parser, підготовка й тести вузького LOG IPC, аналіз каталогів і capture, перевірка джерела SRC/часових якорів. Оператор: фізична ізоляція, окремий дозвіл на power/SD та встановлення/видалення, перевірка плати і знаків довіри, підключення пасивного аналізатора, підтвердження відновлення. Для B3 потрібні окремий допуск, фізична фіксація тяги та кінець фізичного TX за незалежним capture. B3 не виконано.
