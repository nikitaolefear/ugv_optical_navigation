## Software capture boundary

Kernel has CONFIG_USB_MON=m and a matching module. Dry run resolves it. Module not loaded, no usbmon character device present, and no standard capture CLI discovered. No module or debug mount changes and no capture occurred. When authorized, load only usbmon and use a reviewed binary API collector or an approved capture utility, verify access, snap length, ring capacity and kernel/user drop counters. Binary usbmon observes the host stack independently of a serial consumer; it does not open a second tty. Prefer per-bus capture and restrict retained data to the selected endpoint and bounded window. Test collector and decoder with synthetic data before a live run. [Linux usbmon](https://docs.kernel.org/usb/usbmon.html)

Identify the active Owner's tty using the owner descriptor helper and map through sysfs from the CDC communication interface to its companion data interface. On the current Pixhawk the Owner's interface pair is CDC control 02 / data 03, bulk OUT 0x04 and bulk IN 0x84, Full Speed 12 Mbit/s. The other CDC pair has different endpoints. Re-resolve bus and address after any re-enumeration. Preserve the mapping privately and abort attribution on a device reset or descriptor change.

Capture outbound URB submission payload and match its callback by bus, device, endpoint and URB ID. Record status and actual length to distinguish full, partial, cancelled and failed transfers. Reassemble the OUT byte stream across URBs, including frames split across submissions and multiple frames in one transfer. Use MAVLink 1/2 length, message ID, sys/comp/seq, CRC and payload fingerprint; include MAVLink 2 signature bytes where present. Use only bytes covered by successful completion to attribute the latest complete frame at the host layer. Retain submit and completion of the URBs containing its final byte. Unknown ordering, errors, truncation or capture loss makes the interval INCONCLUSIVE. USB completion is a host-controller/driver observation about the transfer and successful byte count. It does not timestamp the last physical byte independently or prove FC-side parsing. A syscall result, TIOCOUTQ=0 and URB completion are separate evidence points. [MAVLink framing](https://mavlink.io/en/guide/serialization.html)

## Clocks, DataFlash and eventual B4

Name the clock used by the selected usbmon capture backend, preserve raw timestamps and sample paired UTC/monotonic clocks before and after. Reject clock steps or addition of unbounded capture skew. Align Owner monotonic with the usbmon interval and separately align hardware via calibrated markers. Acquire fresh nonce-correlated TIMESYNC from 1/1 bracketing relevant intervals; keep both Pi monotonic bounds, UTC, RTT and error. Use the validated FC boot clock mapping to DataFlash TimeUS only for same-boot correlation. Where logging already permits, capture trusted S3SRC1 and XKFS.SS for C=0 and C=1. No LOG_DISARMED change for B3. Missing DataFlash can leave the optional FC-side link INCONCLUSIVE without changing a host-only result.

For a separately approved B4 with DataFlash enabled and verified before TX, use the exact message types and sender timestamps from Owner trace. Join VISION_POSITION_ESTIMATE.usec to VISP.RTimeUS and, if sent, VISION_SPEED_ESTIMATE.usec to VISV.RTimeUS. For delta traffic inspect VISO only when that message path is actually used. Check FMT and firmware variant first. Record misses, duplicate keys, quality, ignore flags, reset counter where present and a pre/post window. A matched record supports receipt by the VisualOdom backend. Ignore/quality and the backend send-to-EKF condition are distinct from actual fusion. Correlate with source observer, both XKFS cores, applicable XKF1–XKF4 and local-position validity; neither USB ACK nor VISP/VISV alone proves EKF aiding.
